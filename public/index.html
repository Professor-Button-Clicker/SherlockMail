    Overview

    SherlockMail v0.9.0 is a forensic email collection tool designed for legal, compliance, and investigative professionals. It supports 7 email protocols, provides comprehensive quality control, cloud attachment detection, RFC 3161 timestamping, and maintains a tamper-evident chain of custody.

    7 Email Protocols IMAP, POP3, EWS, Graph API, Gmail API, Zoho API, JMAP with protocol-level logging
    11-Point QC Verification Collection completeness, hash integrity, duplicates, date consistency, DFIR compliance, and more
    RFC 3161 Timestamps Cryptographic timestamps proving data integrity at collection and export time
    Cloud Attachment Detection Detects Google Drive, OneDrive, SharePoint, Dropbox, and Box links in emails
    Inline Search Engine Boolean, regex, wildcard, fuzzy, proximity, and field-specific search with date ranges
    Differential Collection Incremental collection that skips previously acquired messages by hash/message-ID

    Getting Started

    1. Create a Project — Click "+ New" and fill in case details, target email, and examiner information.
    2. Start a Collection — Go to "Collect" to launch the 9-step collection wizard.
    3. Review Results — Browse collected messages, view chain of custody, run forensic analysis.
    4. Export & Verify — Export to EML/MBOX/MSG/PST/MIME with automatic RFC 3161 timestamps.
    App Password Required

    Most modern email providers require an app-specific password for IMAP/POP3 access. Enable 2FA on the target account and generate an app password in the provider's security settings.

    Quality Control (11 Checks)

    1. Collection Completeness — Verifies all acquisitions completed successfully
    2. Hash Integrity — Confirms SHA-256 hashes on all messages
    3. Duplicate Detection — Identifies messages with identical hashes
    4. Date Consistency — Checks for messages with missing or future dates
    5. Missing Fields — Scans for messages lacking required metadata
    6. Folder Coverage — Ensures all enumerated folders have messages
    7. Export Completeness — Verifies export record counts match
    8. Audit Trail — Validates hash-chained audit log integrity
    9. Encryption Detection — Flags encrypted/signed messages
    10. Write Protection (ISO 27037) — Verifies collection used read-only access (EXAMINE mode)
    11. DFIR Standards Compliance — Checks examiner, legal authority, case ID, hashing, acquisitions
    Forensic Integrity Notice

    SherlockMail never fabricates QC results. All verifications report honest results: PASS or ISSUES_FOUND with detailed diagnostics.

    RFC 3161 Timestamps

    Cryptographic timestamps provide tamper-evident proof that data existed at a specific time:

    • Collection timestamps — Generated after each acquisition
    • Export timestamps — Generated after each export
    • Includes serial number, generation time, hash algorithm, and message digest
    • Conforms to RFC 3161 structure (Internet X.509 PKI Time-Stamp Protocol)
    Internal TSA Limitation

    SherlockMail uses an internal Timestamp Authority. These timestamps prove internal consistency but are not issued by an accredited QTSP (Qualified Trust Service Provider) per ETSI EN 319 421/422. For legally binding timestamps admissible in court, submit hash digests to a production TSA such as DigiCert, Sectigo, or GlobalSign.

    Chain of Custody

    • Each entry includes timestamp, event type, description, and examiner name
    • Each entry's hash = SHA-256(previousHash | timestamp | eventType | description)
    • The chain can be verified at any time — any modification breaks the chain
    • Events: project creation, acquisition, search, QC, export, cloud scan, timestamp, integrity verification

    Evidence Integrity Verification

    Comprehensive verification covering:

    • Message hash verification — SHA-256 integrity on all messages
    • Audit chain verification — Hash-chain integrity on the audit log
    • Export verification — File hash verification on exported files
    • Timestamp records — Count and validity of RFC 3161 timestamps

    Standards: NIST FIPS 180-4, NIST SP 800-86, FRE 901(b)(9) / FRE 902(14), RFC 3161

    Security & Forensic Integrity

    • Credentials transmitted only to configured servers — never stored in plain text
    • TLS enabled by default for all connections
    • SQLite with WAL mode for crash-resistant writes
    • SHA-256 hashing on all messages at acquisition time
    • All exports preserve original MIME source data
    • QC verification provides honest, verifiable results
    • RFC 3161 timestamps for collection and export events

    DFIR Standards Compliance

    SherlockMail is designed to align with established digital forensic and incident response (DFIR) standards and guidelines:

    ISO/IEC 27037:2012

    Guidelines for identification, collection, acquisition, and preservation of digital evidence.

    • Identification — Provider auto-detection and protocol enumeration identify available evidence sources
    • Collection — IMAP EXAMINE mode ensures read-only access; all protocol interactions are logged
    • Acquisition — SHA-256/SHA-512/MD5 triple hashing at acquisition time; per-message integrity verification
    • Preservation — Hash-chained audit log, RFC 3161 timestamps, and tamper-evident chain of custody
    • Four principles — Auditability (full audit trail), Repeatability (documented procedures), Reproducibility (hash verification), Justifiability (legal authority fields)

    NIST SP 800-86

    Guide to Integrating Forensic Techniques into Incident Response.

    • Collection — 9-step wizard ensures systematic collection with documented parameters
    • Examination — Inline search, header analysis, threading, and deduplication tools
    • Analysis — Timeline visualization, relationship mapping, SPF/DKIM/DMARC authentication analysis
    • Reporting — Chain of custody reports, PDF forensic reports, hash manifests

    SWGDE Best Practices (2025)

    Scientific Working Group on Digital Evidence — Best Practices for Digital Evidence Collection (18-F-002-2.0).

    • Legal authority — Projects require legal authority and scope documentation before collection
    • Documentation of changes — Any live collection that alters data is documented in the audit trail
    • Ancillary data — Full email headers, metadata, cloud attachment links, and encryption status are preserved
    • Targeted collection — Query filters, date ranges, and folder selection support defensible scope
    • Cloud evidence — Per SWGDE 23-F-004-1.1, IMAP/API collection from cloud providers is documented as a viable option

    ACPO Good Practice Guide (v5, 2012)

    Association of Chief Police Officers — Good Practice Guide for Digital Evidence.

    • Principle 1 (No alteration) — IMAP EXAMINE mode prevents flag changes; BODY.PEEK[] avoids setting \Seen
    • Principle 2 (Competent access) — Examiner name recorded on all operations; justification fields available
    • Principle 3 (Audit trail) — SHA-256 hash-chained audit log records every action with timestamps
    • Principle 4 (Overall responsibility) — Examiner certification in chain of custody reports

    EDRM (Electronic Discovery Reference Model)

    • Collection Standards — Documented, repeatable collection processes with protocol logging
    • Processing — Deduplication by SHA-256 hash and Message-ID, near-duplicate detection
    • Production — Concordance DAT with Bates numbering (SM-0000001), OPT cross-reference files

    Federal Rules of Evidence (FRE)

    • FRE 901(b)(9) — Process producing accurate result: documented collection, hash verification, QC checks
    • FRE 902(14) — Certified data from electronic process: hash manifests and chain of custody reports

    Important Disclaimer

    SherlockMail generates RFC 3161-structured timestamps internally. For legally binding timestamps with evidentiary weight, connect to a qualified Timestamp Authority (TSA) such as DigiCert, Sectigo, or FreeTSA. Internal timestamps prove internal consistency but lack independent third-party attestation required by some jurisdictions and by ETSI EN 319 421/422.

    Deviation Documentation

    Per SWGDE guidelines, if you encounter situations warranting deviation from standard collection practices, thoroughly document the specifics in the project notes and audit log. SherlockMail logs all protocol interactions and collection parameters automatically, but examiner notes on deviations should be added manually to the chain of custody.
